# auth-ui 0.10.0 — MFA(TOTP) 화면 설계

- 작성일: 2026-11-09
- 상위 설계: `@withwiz/toolkit` `docs/auth/2026-11-08-mfa-totp-design.md`(0.30.0, develop 병합됨). 특히 4-1절(전달 방식별 대기 토큰, auth-ui 계약)과 4-2절(잠금).
- 대상 저장소: `withwiz-auth-ui`(현재 0.9.0), 브랜치 `feat/mfa-ui`.

## 1. 목적

toolkit 0.30.0 이 서버 쪽 2단계 인증(TOTP + 복구 코드)을 제공한다. auth-ui 는 그 화면을 제공해, binder·tavlet 등 소비 앱이
같은 코드 입력 흐름과 같은 등록·해제 흐름을 직접 만들지 않고 쓰게 한다. 등록 흐름(QR → 코드 확인 → 복구 코드 저장)은
틀리기 쉬우므로 한 곳에서 만든다(사용자 결정: 관리 화면까지 auth-ui 가 제공).

## 2. 목표 · 비목표 · 반목표

**목표**
- 비밀번호 로그인 중 `MFA_REQUIRED` 를 받으면 같은 카드에서 코드 입력 단계로 바뀐다.
- OAuth 로그인 뒤 toolkit 이 보내는 `urls.mfaChallenge` 페이지에 쓸 코드 입력 화면을 제공한다.
- 계정 설정에 넣을 MFA 관리 컴포넌트(상태·등록·복구 코드·해제·재발급)를 제공한다.
- `AuthProvider` 에 `verifyMfa` 를 추가하고, `login()` 이 MFA 가 필요할 때 구분 가능한 오류를 던진다.
- ko/en/ja 문구, 기존 폼과 같은 `classNames`·`slots`·`unstyled`·`locale`·`messages` 사용자화.

**비목표**
- 어떤 사용자에게 MFA 를 요구할지 같은 정책(binder 몫).
- 운영자용 MFA 초기화 화면(toolkit `resetMfa` 를 소비 앱이 직접 쓴다).
- WebAuthn·SMS 등 다른 2단계 수단.
- 재인증(step-up) 화면.

**반목표**
- `mfa` 를 쓰지 않는 소비 앱의 로그인 동작·모양이 0.9 와 달라지면 안 된다.
- 복구 코드·비밀 키를 브라우저 저장소(localStorage·sessionStorage)에 남기면 안 된다.
- 대기 토큰(`mfaToken`)을 URL 에 싣거나 저장소에 남기면 안 된다(메모리에서만 다룬다).

## 3. 서버 계약 (toolkit 0.30.0)

경로는 모두 `apiBasePath`(기본 `/api/auth`) 아래다. 요청은 기존 `authFetch` 처럼 `credentials: 'include'`.

| 동작 | 요청 | 성공 | 주요 실패 |
|---|---|---|---|
| 로그인 1단계 | `POST /login` | 200(세션) | 401 `MFA_REQUIRED`(본문 최상위 `mfaToken` 은 header·hybrid 모드에서만, cookie·hybrid 는 `mfa_pending` 쿠키) |
| 코드 검증 | `POST /mfa/verify` `{code}` 또는 `{recoveryCode}`, 쿠키가 없으면 본문 `mfaToken` | 200 + 세션, OAuth 출신이면 본문 `redirectTo` | 401 `MFA_INVALID_CODE`, 401 `MFA_PENDING_EXPIRED`, 429 `MFA_LOCKED`(+`retryAfter`) |
| 상태 | `GET /mfa` | `{enabled, recoveryCodesRemaining}` | 401, 404 `MFA_NOT_CONFIGURED` |
| 등록 시작 | `POST /mfa/setup` | `{secret, otpauthUri}` | 409 `MFA_ALREADY_ENABLED` |
| 등록 확정 | `POST /mfa/enable` `{code}` | `{recoveryCodes}` | 401 `MFA_INVALID_CODE`, 409, 429 |
| 해제 | `POST /mfa/disable` `{code}` 또는 `{recoveryCode}` | `{success}` | 401, 409 `MFA_NOT_ENABLED`, 429 |
| 복구 코드 재발급 | `POST /mfa/recovery-codes` `{code}` | `{recoveryCodes}` | 401, 429 |

- 코드 형식: 6자리 숫자. 복구 코드: `xxxx-xxxx`(입력은 대소문자·공백·하이픈 무관, 1..32자).
- `/me` 는 MFA 기능이 켜진 소비 앱에서 `mfaEnabled` 를 준다.

## 4. 접근 방식

**로그인 중 코드 입력 위치**(사용자 선택: 가)
- 가. **로그인 폼 안에서 2단계로 전환** — 채택. header 모드의 `mfaToken` 을 메모리에만 둔다. 코드 입력부는 공용
  `MfaChallengeForm` 으로 만들고 OAuth 용 화면도 같은 컴포넌트를 쓴다.
- 나. 항상 코드 입력 페이지로 이동 — 흐름은 하나지만 header 모드에서 토큰을 `sessionStorage` 로 옮겨야 하고 이동이 한 번 는다.

**QR 표시**(사용자 선택: 가)
- 가. **`uqr`(MIT, 런타임 의존성 0) 로 QR 행렬을 얻어 자체 SVG 로 그린다** — 채택. 비밀 키 문자열도 함께 보여 직접 입력을
  지원한다. 소비자는 `renderQr` prop 으로 대체할 수 있다.
- 나. `qrcode.react` — 쓰기 쉽지만 공개 의존성이 늘어난다.
- 다. `renderQr` 필수 — 의존성 0 이지만 모든 소비자가 라이브러리를 골라야 한다.

## 5. 구성 요소

### 5-1. `MfaChallengeForm`(신규, `components`)
- 코드 입력 1개(숫자 6자리, `inputMode="numeric"`, `autoComplete="one-time-code"`), "복구 코드로 로그인" 전환(텍스트 입력),
  "처음부터 다시" 링크(`loginUrl`, 기본 `/login`).
- props: `mfaToken?`(header 모드에서 받은 토큰, 메모리 전달), `apiBasePath`, `redirectAfterLogin`(기본 `/`), `loginUrl`,
  `locale`, `messages`, `className`, `classNames`, `unstyled`, `forceColorScheme`, `slots`(header/footer/beforeForm/afterForm),
  `hooks`(`AuthFormHooks<{ method: 'code' | 'recoveryCode' }>`: `onBeforeSubmit`, `onSuccess`, `onError`), `onRestart?`
  (지정하면 "처음부터 다시"가 링크 대신 이 콜백을 부른다 — 로그인 폼 안에서 1단계로 돌아갈 때 쓴다).
- 성공: `onSuccess(user, {body})` 의 반환 경로 → 본문 `redirectTo` → `redirectAfterLogin` 순으로 이동(기존 `pickRedirectTarget`·
  `safeRedirectTarget` 재사용).
- 실패 처리:
  - `MFA_INVALID_CODE`: 입력란 오류 문구, 입력값 비움, 포커스 유지.
  - `MFA_PENDING_EXPIRED`: "인증 시간이 지났습니다" 문구 + 제출 비활성 + "처음부터 다시" 강조.
  - `MFA_LOCKED`: `retryAfter` 를 분 단위로 올림해 보여 주고 제출 비활성(카운트다운은 하지 않는다 — 내 판단: 단순함).
  - 그 밖·네트워크: 기존 `readAuthError`/`networkAuthError` 경로.
- 6자리를 다 입력하면 자동 제출하지 않는다(내 판단: 실수 제출이 실패 횟수에 들어가므로 명시적 제출).

### 5-2. `LoginForm` 변경
- 응답이 401 이고 `key === 'MFA_REQUIRED'` 이면 오류로 보지 않고 2단계로 바꾼다. 본문 최상위 `mfaToken`(문자열일 때만)을
  상태에 담아 `MfaChallengeForm` 에 넘기고 `onRestart` 로 1단계 복귀(입력값 유지, 비밀번호는 비움).
- 2단계에서는 OAuth 버튼·구분선·하단 링크를 숨기고, 헤더 제목을 MFA 문구로 바꾼다. `slots.header` 를 준 소비자는 그대로 둔다.
- `hooks.onSuccess` 는 2단계 성공 시점에 부른다(세션이 생긴 시점). `hooks.onError` 는 각 단계의 실패에서 부른다.
- 새 prop `mfaMessages?: Partial<AuthMessages['mfa']>`.
- `MFA_REQUIRED` 가 오지 않는 소비자에게는 변화가 없다.

### 5-3. `MfaChallengeScreen`·`MfaChallengePage`(신규, `screens`·`pages`)
- 기존 `LoginScreen` 처럼 `AuthLayout` 으로 `MfaChallengeForm` 을 감싼다. OAuth 출신은 `mfa_pending` 쿠키로만 오므로
  `mfaToken` 없이 동작한다. `pages` 는 기존 패턴과 같은 얇은 래퍼.

### 5-4. `MfaSettings`(신규, `components`)
상태 기계 하나로 관리 화면 전체를 그린다.

```
loading → (GET /mfa)
  ├ 404 MFA_NOT_CONFIGURED → 아무것도 그리지 않는다(slots.notConfigured 로 대체 가능)
  ├ 401 → hooks.onUnauthenticated?() 후 안내 문구
  ├ disabled → [2단계 인증 켜기]
  │     → setup: QR + 비밀 키(복사 버튼) + 코드 입력 → enable
  │     → recoveryCodes: 코드 10개 + [복사] [다운로드(.txt)] + "저장했습니다" 체크 후 [완료]
  └ enabled(남은 복구 코드 N개, 3개 이하면 경고) → [복구 코드 다시 만들기] [2단계 인증 끄기]
        → regenerate: 코드 입력 → recoveryCodes 단계
        → disable: 코드 또는 복구 코드 입력 → disabled
```

- props: `apiBasePath`, `issuerLabel?`(QR 아래 안내용 표시명, 기본 없음), `renderQr?: (otpauthUri: string) => ReactNode`,
  `locale`, `messages`, `className`, `classNames`, `unstyled`, `forceColorScheme`, `slots`(header/footer/notConfigured),
  `hooks`: `onEnabled?()`, `onDisabled?()`, `onRecoveryCodesRegenerated?()`, `onError?(text, info)`, `onUnauthenticated?()`.
- 복구 코드는 컴포넌트 상태에만 두고, [완료] 를 누르면 지운다. 저장소에 쓰지 않는다.
- setup 도중 이탈하면 서버에 진행 중 비밀 키가 남지만 활성화되지 않으므로 그대로 둔다(다음 setup 이 교체).
- 잠금·오류 표시는 5-1 과 같은 규칙.

### 5-5. `MfaQrCode`(내부, 공개하지 않음)
- `uqr` 의 `encode(otpauthUri)` 로 행렬을 얻어 `<svg>` 의 `<path>` 하나로 그린다. 여백 4모듈, 크기 prop, `role="img"`·
  `aria-label`(문구에 "인증 앱으로 스캔"), 색은 CSS 변수(`--wiz-auth-fg`/`--wiz-auth-bg` 계열 기존 토큰 재사용).

### 5-6. `AuthProvider` 변경
- `login()`: 401 `MFA_REQUIRED` 면 `AuthError`(key `MFA_REQUIRED`)를 던지되, 본문 `mfaToken` 이 있으면 `AuthError` 에 담는다
  (새 선택 필드 `mfaToken?`). 소비자는 이것으로 2단계를 그린다.
- `verifyMfa(proof: { code: string } | { recoveryCode: string }, opts?: { mfaToken?: string }): Promise<{ redirectTo?: string }>`
  — 성공하면 사용자 상태를 갱신하고 `onAuthChange(true)`. 실패는 `AuthError`.
- `AuthContextValue.user` 에 `mfaEnabled?: boolean` 추가(`/me` 가 줄 때만).

### 5-7. i18n
- `AuthMessages.mfa` 신설(ko/en/ja): 제목·안내·입력 라벨·복구 코드 전환·처음부터 다시·제출/진행 중·오류(잘못된 코드,
  만료, 잠금 `{minutes}`)·관리 화면 문구(켜기·끄기·QR 안내·비밀 키·복사됨·다운로드·저장 확인·남은 코드 경고·재발급).
- ko 기본 문구는 toolkit 의 서버 문구와 같은 어조(예: "인증 앱의 6자리 코드를 입력하세요", "코드가 올바르지 않습니다",
  "인증 시간이 지났습니다. 다시 로그인하세요", "시도가 너무 많습니다. {minutes}분 뒤 다시 시도하세요").

## 6. 제약

- 새 런타임 의존성은 `uqr` 하나만. 정확한 버전으로 고정(`0.1.3`)한다 — 소비 저장소들이 `minimumReleaseAgeExclude` 를 쓰므로.
- 공개 경로: `components`·`screens`·`pages`·`i18n`·`types` 의 기존 진입점에 추가한다(새 서브패스 없음).
- 접근성: 기존 `fieldErrorA11y`·`role="alert"` 규칙, 단계 전환 시 첫 입력란으로 포커스 이동.
- 스타일: 기존 `wiz-auth-*` 클래스 체계와 CSS 변수. 새 클래스는 `wiz-auth-mfa-*`.
- 0.9 동작 유지: `MFA_REQUIRED` 가 없는 응답 경로는 바뀌지 않는다(기존 테스트 무변경 통과).
- 버전 0.10.0, CHANGELOG·README(Migration: `login()` 의 `MFA_REQUIRED`, 새 컴포넌트, binder·tavlet 디스패치 예시).

## 6-1. 검토에서 정한 사항 (설계자 판단)

- **관리 화면은 쿠키 인증만 지원한다.** 현재 소비 앱은 모두 쿠키를 쓴다(tavlet·galpi `tokenDelivery: "cookie"`, binder 는
  기본값 hybrid). `MfaSettings` 는 기존 `authFetch`(`credentials: 'include'`)로 요청한다. header 전용 소비 앱용 토큰 주입
  prop 은 만들지 않고 README 에 "관리 화면은 access 쿠키가 필요하다"고 적는다(필요해지면 `fetcher` prop 을 나중에 추가).
- **새 컴포넌트는 `AuthProvider` 없이 동작한다.** 기존 폼과 같다. 서버 호출과 응답 해석은 공용 유틸 `src/utils/mfa-api.ts`
  하나에 두고(`verifyMfa`·`getMfaStatus`·`setupMfa`·`enableMfa`·`disableMfa`·`regenerateRecoveryCodes`, 실패는 `AuthErrorInfo`
  로 정규화하고 `retryAfter`·`mfaToken` 을 함께 읽는다), `MfaChallengeForm`·`MfaSettings`·`AuthProvider.verifyMfa` 가 모두
  이것을 쓴다. `MfaSettings` 는 Provider 의 `user.mfaEnabled` 를 갱신하지 않는다(필요하면 소비자가 `onEnabled`·`onDisabled`
  훅에서 다시 조회한다).
- `AuthErrorInfo` 에 선택 필드 `retryAfter?: number` 를 추가한다(`MFA_LOCKED` 본문 최상위 값). `mfaToken` 은 오류 정보가 아니라
  `LoginForm` 이 본문에서 직접 읽는다.
